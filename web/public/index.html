One memory for every AI agent you run

MemoryLoom gives all your AI agents the same memory, so a fact learned by one agent is known by every agent you run.

Ask what your agents know and each answer shows where it came from, so you can trust it or challenge it. Correct a fact once and every agent works from the correction, not from the old fact. It remembers what the team believed in the past as well, so you can ask what was believed on any earlier day.

MemoryLoom is for people who work with AI agents every day. It is for founders and operators and researchers and support leads and small team leads who run more than one agent and need those agents to agree on the facts.

The demonstration runs on a small fictional corpus, a community demo rig called Project Lantern, tended by two agents named grok and moose. Everything on this page that shows data is read live from that corpus in the database, not from a picture of it.

How to start

Your first day with MemoryLoom

Three things, in the order you will do them. Nothing here needs setting up before your first conversation on this demo.

Talk

Open chat and say things the way you would say them to a colleague. Tell it a fact about your work and it will be checked before it is kept. There is nothing to set up before your first conversation.

Ask

Ask a question in plain words and read the answer at the top. Under the answer you can open the proof and see which record the answer came from and who wrote it. If nothing solid is stored, it tells you so instead of guessing.

Correct

When a fact is wrong, say the right fact in chat. Once the correction is kept, every agent you run works from the new fact. The old fact stays readable, so you can still see what the team used to believe.

Everyday use

What it does for you, day to day

Four ordinary moments, in the words of the person living them.

One memory shared by every agent you run

You run one agent for research and one for writing and one for support. A fact found by the research agent in the morning is known to the support agent in the afternoon. Nobody copies notes between tools.

Ask what was decided and get the proof

You ask what the team decided about a price or a date or a plan. The answer names the record it came from and the person or agent who wrote it. You can open the record and read what the answer rests on.

Correct a fact once and every agent sees it

A venue changes or a deadline moves or a name was wrong. You give the correction once in chat. From then on every agent answers with the new fact, and the old fact is kept where you can still read it.

Rewind to any past date

A client asks why a decision was made last month. You pick the date and read what the team believed on that day. You can show what was known then, even when the team believes something different now.

How it works

How MemoryLoom works

Agents suggest what they have learned. Each suggestion is checked before it can become part of the shared memory. What passes the check is written once and is never edited after that. When a fact is replaced, the old fact stays readable with its dates. Every answer shows the record it came from. The team also keeps a log of its interactions, and lessons drawn from that log go through the same check before they can guide future answers.

The corpus woven above is a synthetic demo corpus. Every record in it is fictional, written for this demonstration.

Suggestions and the check

An agent or a person suggests a fact. The check accepts it or turns it away or passes it to a person to decide. Only accepted facts become part of the shared memory. The check is the Jev decision service, and its reasons are kept with the record. When the check cannot be reached, nothing is approved in its place, and the suggestion waits for a person instead.

Written once

An accepted fact is written as one record and the record is never edited. When the team learns better, a new record takes its place. The old record stays as it was written.

Proof with every answer

Every answer carries its proof. The proof names the record the answer came from and who wrote it and what it rests on. An answer with no proof behind it is not shown as an answer.

Learning

Learning from the log

Interactions are logged as they happen. Lessons drawn from the log are suggested in the same way as any other fact. A lesson guides future answers only after it passes the same check.

Provenance

Every interaction is logged as an event in an append only log. Events are never edited or deleted, so the story of any improvement can always be read again.

The gate

When an episode teaches something general, a lesson is proposed from it and decided by the same gate as a memory. Only a gate decision can make it a standing lesson.

Audit

A lesson written in by any other route is caught by the audit and quarantined. It never stands as approved.

Recall

An approved lesson is a memory like any other. The next agent recalls it by receipt and works differently because of it.

Decay

A lesson that stops being used decays on the same schedule as every other memory, and the gate decides whether it is kept or dropped.

In plain terms. Grok lodged a claim citing no evidence and was escalated. The correction was written down in the same turn. The episode became a lesson only after the gate approved it. Moose, a different agent, then lodged a claim of the same kind and was approved first try, because the lesson was recalled, with its receipt, before acting.

Limits

What MemoryLoom does not do

MemoryLoom answers from the records it holds. When nothing solid is stored, it says so instead of guessing. It does not settle arguments between records on its own, and a person decides the proposals the check passes on. The public demo runs on a small set of records about Project Lantern, so demo answers show the shape of the product rather than the size of a real team memory.

For developers

Run it, then paste your keys in Settings

You need Node 22 or later and Postgres 16 with pgvector. Copy the example settings file to your local settings file and set your database address there. Then install and prepare and seed and start with the commands below. Setup is done once. After that, one command starts the whole app, this site at / and the console at /console.

cp .env.example .env.local   # set DATABASE_URL (Postgres 16 + pgvector)
npm install
npm run db:init                                  # schema + migrations
DATABASE_URL=postgres://… npm run seed:web   # the Project Lantern demo corpus + its learning story
DATABASE_URL=postgres://… npm run web       # the one command: site + console

Provider keys, the standard way. MemoryLoom runs with no keys at all. The demo corpus, recall, the graph and time travel all work on your machine. One part is recorded, not live. The learning story in Fig. 3 is recorded at seed time, and recording it needs the gate. Seed with a Jev key configured in Settings or set in the environment and the full story is recorded. Seed without one and the seed prints a notice saying the story was not recorded, while everything else still works. To switch on the hosted providers, open the console, go to Settings, and paste your own key for each provider. A Meta Model API key comes from dev.meta.ai, a Jev key from TypeSafe, and a Baseten key from the Baseten workspace settings. Use Test connection on each one before you rely on it.

Where the keys live. Keys pasted into Settings are stored in .env.local in the app folder, on your machine only, with file permissions 0600. The file is git ignored and never committed. Settings shows only the last four characters of a saved key, and keys are never written to any log. An environment variable (META_MODEL_API_KEY, TYPESAFE_API_KEY, BASETEN_API_KEY) can be set instead and wins over Settings. Settings can only be changed from the local app. A hosted deployment cannot change them.

Agents connect over MCP (npm run mcp) and speak the same propose, recall and review surface the console renders. The console displays decisions. It never makes or overrides one.

MemoryLoom. One memory for every AI agent you run, with the proof kept for every answer. Data lives in one Postgres store on your own machine. The demonstration corpus, Project Lantern, is fictional, written for this demo, and no real data appears anywhere on this site or in the console.
