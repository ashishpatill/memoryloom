Agent teams forget. This one doesn’t.

MemoryLoom is one shared, auditable memory for a team of AI agents — it helps teams whose agents work across many sessions by giving every agent the same record of what the team knows, why it believes it, and what it believed before.

See it working Read the proof

The demonstration runs on a small fictional corpus — a community demo rig called Project Lantern, tended by two agents, grok and moose. Everything on this page that shows data is rendered live from that corpus in the database, not from a picture of it.

01 — How it helps

Three things that stop going wrong

A team of agents without a shared memory loses knowledge in three ordinary ways. MemoryLoom is built so each of them has a plain answer.

No more cold starts

Every session used to begin from nothing, so yesterday’s hard-won fact — the rig runs firmware 2.4.1 — was re-derived, re-asked, or quietly contradicted. Here, an agent starting work recalls what the team already holds, with the record it came from.

One memory, not many notebooks

Each agent used to remember alone, in its own format, where no other agent could read it. Here there is one store, written one way, that every agent on the team reads and proposes to.

Every belief has a “why”

When two agents disagreed, there was no record of who claimed what, on what evidence, or who approved it. Here every memory keeps its author, its cited evidence and its decision, so the question is answered from the record, not restarted from zero.

02 — How it works

Nothing enters memory unexamined

One loop, run the same way every time: an agent proposes, a gate decides with its reasons recorded, truth is written once, and recall answers with receipts.

An agent proposes a memory; it never writes directly. The gate — the Jev decision service, see Providers — scores the proposal and answers with one fixed choice: approve, reject, or escalate to a human. Escalate always exists, and on any gate failure the proposal queues for a human instead of being approved. The gate’s reasons are kept with the record.

An approved memory is written once into the truth store: an append-only record carrying who proposed it, the evidence it cites, and the dates it is believed between. Nothing edits it afterwards; a belief that changes is superseded by a new record, and the old one stays readable. The recall index is derived from truth and can be rebuilt from it at any time, so a rebuild is routine, not an incident.

When an agent asks a question, recall answers with receipts: each result names the record it came from, who wrote it, and what it rests on. A result that cannot produce its receipt is dropped before the agent sees it.

The words, defined once

These seven nouns are spelled the same way here, in the console and in the README. Everything else on this page is built from them.

NounWhat it is
memoryOne recorded belief: its text, who proposed it, the evidence it cites, and the dates it was believed between.
proposalA memory an agent asks to add. It is not in the store until the gate approves it, or a human approves an escalation.
gateThe decision step every proposal crosses. It answers approve, reject, or escalate, and its reasons are recorded with the outcome.
receiptThe proof attached to a recalled memory: the record it came from, who wrote it, and what it rests on. No receipt, no answer.
recallAsking the store a question. It searches the index derived from truth and returns memories with their receipts.
namespaceOne team’s separate memory space inside the store. The demo corpus lives in its own namespace, apart from any real work.
playbookThe standing lessons the team has earned. A lesson is a memory like any other — proposed, gated, recalled, and decayed the same way (see Learning).

03 — Learning

The app itself gets better, on the record

MemoryLoom does not just store what agents know. It keeps a record of how the team worked, and turns that record into standing lessons — carefully, in the open, and only through the same gate as everything else.

Every interaction is logged as a provenance event: a proposal, a gate verdict, a correction made in the same turn, a recall that hit or missed. The log is append-only — events are never edited or deleted, so the story of an improvement can always be re-read. When an episode teaches something general, a lesson is proposed from it and gated like a memory: the Jev gate decides whether it becomes a standing playbook lesson, and a lesson written in by any other route is caught by audit and quarantined. An approved lesson is a memory, so the next agent recalls it by receipt and behaves differently; and because it is a memory, a lesson that stops being used decays on the same schedule as everything else, with the gate deciding keep or drop. Improvement here is not asserted — it is shown, event by event, below.

In plain terms: grok lodged a claim citing no evidence and was escalated; the correction was written down in the same turn; the episode became a lesson only after the gate approved it; and moose, a different agent, then lodged a claim of the same kind and was approved first try — because the lesson was recalled, with its receipt, before acting.

04 — Providers

Two working parts, named honestly

MemoryLoom’s own code holds the memory, the gate logic and the record. Two outside services do the model work and the deciding, and each is named for exactly what it does — no more.

ProviderWhat it does hereWithout its key
Meta Model API
model muse-wonder-1.0 — the only Meta model this build uses		Thinking work, in two tiers of the same model: Wonder Full (high effort) writes consolidations, narrates recall answers and explains contradictions; Wonder (medium effort) handles triage and implementation passes. Every call goes through the router, is spend-logged and content-hash cached.The local provider covers model work offline. The demo, recall, the graph and time travel all run with no key at all.
Jev
TypeSafe decision API, jev-1.13.0		Deciding work: every decision that has a fixed set of answers goes to Jev — the write gate (approve / reject / escalate), consolidation accept, decay keep / drop, and lesson promotion. Its scores are calibrated before thresholds go live, and its reasons are recorded.There is no local fallback that approves. With no key, or on any Jev failure, the gate fails closed and proposals queue for a human.

And the parts that are not working parts, stated plainly: a Baseten key can be stored and tested in Settings, but the Baseten lane is parked — its grant key serves only a model this build does not use — so no product path calls Baseten and its spend is $0. Fireworks and Modal have no role in this build.

06 — Get started

Run it, then paste your keys in Settings

You need Node 22+ and a Postgres 16 database with the pgvector extension. Setup is done once; after that, one command starts the whole app — this site at /, the console at /console.

cp .env.example .env.local   # set DATABASE_URL (Postgres 16 + pgvector)
npm install
npm run db:init                                  # schema + migrations
DATABASE_URL=postgres://… npm run seed:web   # the Project Lantern demo corpus + its learning story
DATABASE_URL=postgres://… npm run web       # the one command: site + console

Provider keys, the standard way. MemoryLoom runs with no keys at all — the demo corpus, recall, the graph and time travel all work on your machine. One part is recorded, not live: the learning story in Fig. 3 is recorded at seed time, and recording it needs the gate — seed with a Jev key configured in Settings (or set in the environment) and the full story is recorded; seed without one and the seed prints a notice saying the story was not recorded, while everything else still works. To switch on the hosted providers, open the console, go to Settings, and paste your own key for each provider: a Meta Model API key from dev.meta.ai, a Jev key from TypeSafe, a Baseten key from the Baseten workspace settings. Use Test connection on each one before you rely on it.

Where the keys live. Keys pasted into Settings are stored in .env.local in the app folder, on your machine only, with file permissions 0600. The file is git-ignored and never committed; Settings shows only the last four characters of a saved key; and keys are never written to any log. An environment variable (META_MODEL_API_KEY, TYPESAFE_API_KEY, BASETEN_API_KEY) can be set instead and wins over Settings. Settings can only be changed from the local app — a hosted deployment cannot change them.

Agents connect over MCP (npm run mcp) and speak the same propose / recall / review surface the console renders. The console displays decisions; it never makes or overrides one.

MemoryLoom — one shared, auditable memory brain for agent teams. Data lives in one Postgres store on your own machine; the demonstration corpus (Project Lantern) is fictional, written for this demo, and no real data appears anywhere on this site or in the console.
